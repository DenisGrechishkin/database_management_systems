# SQL и базы данных: учебные проекты

В этом репозитории шесть работ по курсу «Системы управления базами данных». Вместе они показывают путь от первых `SELECT` до работы с миллионом строк, транзакциями и защитой данных. Всё сделано на **PostgreSQL** на учебной базе вуза: студенты, преподаватели, дисциплины, оценки, структурные подразделения.

## Что я умею (и где это видно)

| **Проектирование БД** | ER-модель, нормализация, связи 1:1 / 1:N / N:N, первичные и внешние ключи, `CHECK`, `UNIQUE`, `DEFAULT` | ЛР 2 |

## Работы

### ЛР 1. Объединяющие и вложенные запросы
**Что делал:** писал аналитические запросы к базе вуза.
- Список студентов с дисциплинами и оценками.
- Средний балл студентов, родившихся в 2004 году, с сортировкой по убыванию.
- Преподаватели, у которых нагрузка больше 5 дисциплин (`GROUP BY` + `HAVING`).
- Преподаватели со стажем выше среднего и зарплатой ниже среднего, плюс строка со средними значениями.
- Максимальный размер группы по вузу (вложенный запрос).
- Единый список женщин вуза (преподаватели и студенты) с определением пола по окончаниям (`UNION ALL`, `LIKE`).
- Создал три представления (`VIEW`) для типовых отчётов.

**Результат:** освоил основной набор SQL для аналитики и разобрал на практике, чем `COUNT(col)` отличается от `COUNT(*)` в части `NULL`.

### ЛР 2. Логическая и физическая модель БД
**Что делал:** дорабатывал структуру базы.
- Исправил допущение «одна дисциплина, один преподаватель»: сделал отдельную таблицу и связал её с дисциплинами и преподавателями.
- Добавил студентам телефон с `CHECK`-ограничением по регулярному выражению `8(XXX)XXX-XX-XX`.
- Спроектировал модуль «курсы повышения квалификации преподавателей»: 3 новые таблицы (курсы, сертификаты, связь преподавателей и курсов) с ключами, `ON DELETE CASCADE` и проверками дат.
- Построил ER-схему обновлённой базы.

**Результат:** научился переходить от бизнес-задачи к схеме данных и закреплять правила на уровне самой БД.

### ЛР 3. Операторы модификации данных
**Что делал:**
- `UPDATE` с несколькими вложенными запросами: помечал преподавателей, у которых средний балл по их дисциплинам ниже среднего по подразделению.
- Автоматически сгенерировал телефоны всех студентов по заданным правилам (код оператора зависит от чётности студенческого, остальные цифры зависят от случайного числа, номера группы и её размера).
- Наполнил новые таблицы осмысленными тестовыми данными (по 10+ строк в каждой).

**Результат:** уверенно работаю с `UPDATE ... FROM`, CTE и массовой подготовкой данных.


---

### ЛР 4. PL/pgSQL: процедуры, функции, триггеры
**Что делал:**
- Сравнил расчёт среднего балла на чистом SQL и в PL/pgSQL.
- Скрипт-статистика: количество дней рождений по месяцам.
- Симуляция шахматного турнира: 10 случайных студентов, игра каждого с каждым, случайные результаты, итоговая таблица очков.
- Процедура продления студенческих билетов целой группе (параметр: номер группы).
- Функции: зарплата преподавателя по ID, студенты с числом двоек выше заданного порога.
- Триггеры: запрет двойки для студента с заданным именем, запрет латиницы в ФИО, защита от удаления записи.

**Результат:** умею упаковывать повторяющуюся логику в процедуры и функции и «зашивать» бизнес-правила в базу триггерами.


---

### ЛР 5. Индексы и транзакции
**Что делал:**
- Создал таблицу посещаемости и **заполнил её 1 000 000 строк** сгенерированных данных.
- Измерял время запросов через `EXPLAIN ANALYZE` до и после создания индексов.
- Исследовал селективность. Запрос по одному студенту после индекса `person_id` ускорился **примерно в 24 раза** (148,5 мс → 6,3 мс).
- Заметил обратную сторону индексов: вставка стала чуть медленнее (≈ ×1,15).
- Проверил, что индекс не помогает при фильтре по окончанию строки (`regexp 'a$'`), и разобрал план запроса.
- Работал с двумя параллельными сессиями: `BEGIN` / `COMMIT` / `ROLLBACK`, все четыре уровня изоляции, наблюдение за аномалиями чтения.

**Результат:** понимаю, что индекс ускоряет чтение выборочных запросов, но стоит ресурсов на запись, и умею проверить это измерением, а не на веру.

### ЛР 6. Приложение на C для работы с БД и защита от SQL-инъекций
**Что делал:**
- Написал консольное приложение на C/C++ с подключением к PostgreSQL через `libpq`.
- **Воспроизвёл SQL-инъекцию** и сравнил четыре способа защиты: замена кавычек, экранирование, проверка ввода и параметризованные запросы (`PQexecParams`).
- Добавил предупреждение пользователю при попытке инъекции.
- Перевёл запросы приложения на представление (`VIEW`).
- Создал две роли: `junior` (только чтение) и `admin` (полные права), добавил авторизацию по логину и паролю.
- Реализовал CRUD по оценкам для администратора и просмотр и поиск оценок для обычного пользователя.

**Результат:** понимаю, как данные попадают из приложения в базу, как это можно взломать и как разграничивать доступ. Для аналитика это важно, потому что он работает с данными, которые нельзя ни потерять, ни утечь.
